# Structured Context and UML for LLM-Generated Software

This repository accompanies an MSc dissertation investigating whether structured
context — and specifically UML diagrams — improves the quality of software
generated by large language models. It contains the three input conditions, the
test suite used to evaluate functional correctness, and all fifteen generated
builds.

## The study in brief

A single backend application — a fintech peer-to-peer payments wallet (Python,
FastAPI, SQLite) — was generated by five large language models under three input
conditions:

- **Prose** — a natural-language client-style brief.
- **Structured** — the same requirements as a formal specification.
- **Structured + UML** — the specification plus four UML diagrams (supplied as
  PlantUML text).

The five models were Gemini 3.1 Pro, GPT-5.5 High, Claude Opus 4.8, DeepSeek V4,
and z.ai GLM-5.2. Three conditions across five models gives **fifteen generations**
in total. Each build was evaluated on functional correctness, hallucinations,
security, and code quality.

## Running a build against the test suite

The tests are black-box: they talk to a running build only over HTTP, so the same
suite runs unchanged against every build.

1. Install the build's dependencies (each build includes its own requirements
   file):
   pip install -r <model>/<condition>/requirements.txt

2. Start the build's server (typically):
   uvicorn main:app --port 8000

3. In a separate terminal, point the suite at the running build and run it:
   BASE_URL=http://localhost:8000 pytest tests/

The suite reports how many of the 45 tests passed.

## Running the security and quality checks

Security and code quality were assessed with static-analysis tools run directly
against each build's source, so no running server is needed.

**Security (Bandit).** Bandit scans Python source for common security weaknesses
and reports them by severity (low, medium, high):

pip install bandit\
bandit -r 

**Code quality (Radon).** Radon reports average cyclomatic complexity and a
maintainability index, each on an A–F scale. Complexity reflects how tangled the
logic is; maintainability reflects how easily the code can be read and changed:

pip install radon\
radon cc .   (average cyclomatic complexity - per function, with a summary average)\
radon mi .   (maintainability index - per file)
